# Architecture feature-selection guide

Bounded comparative guide over six independently assessed repositories: [21st-dev/1code](../../corpus/map/repos/21st-dev/1code.md), [aannoo/hcom](../../corpus/map/repos/aannoo/hcom.md), [anomalyco/opencode](../../corpus/map/repos/anomalyco/opencode.md), [bombap/tiny-agent](../../corpus/map/repos/bombap/tiny-agent.md), [openai/codex](../../corpus/map/repos/openai/codex.md), and [strands-agents/harness-sdk](../../corpus/map/repos/strands-agents/harness-sdk.md). Six evidence-linked repositories, not a claim of global top candidates. Every repository-specific sentence cites its exact GitHub source URL from the frozen evidence context; these comparisons are frozen at those commits, while the linked live profiles may evolve. A facet missing from a repository's evidence is unknown, not an absent capability — a blank cell means "not evidenced here," not "unsupported."

## How to use this

Per theme: read the comparison, then answer the decision questions before picking a feature to prototype. Nothing here means the code was run, a security boundary was verified, or an agent is recommended for adoption — it orients a design conversation.

|---|---|---|

| strands-agents/harness-sdk | Invoke model, execute requested tools, feed results back, repeat — [agent-loop.mdx](https://github.com/strands-agents/harness-sdk/blob/08ed4cfd3eb42ae9f668595e675d5f196eee7e44/site/src/content/docs/user-guide/concepts/agents/agent-loop.mdx#L29-L29) | Turn/token invocation limits, mid-loop cancellation, stop reasons, concurrent-invocation guards, hooks, retry strategies — [same doc](https://github.com/strands-agents/harness-sdk/blob/08ed4cfd3eb42ae9f668595e675d5f196eee7e44/site/src/content/docs/user-guide/concepts/agents/agent-loop.mdx#L19-L25) |
| openai/codex | Root-conversation authorization for MultiAgent V2 workers, per a Rust `root_user_authorization` implementation — [user_authorization.rs](https://github.com/openai/codex/blob/6f39a47bb3b04de4c804187bfbf55edc56939aab/codex-rs/core/src/agent/control/user_authorization.rs#L32-L46) | Root thread history filtered (excludes summaries and `<user_action>`-prefixed messages) and capped at `MAX_ROOT_MESSAGES` = 8 — [#L48-L230](https://github.com/openai/codex/blob/6f39a47bb3b04de4c804187bfbf55edc56939aab/codex-rs/core/src/agent/control/user_authorization.rs#L48-L230), [#L30](https://github.com/openai/codex/blob/6f39a47bb3b04de4c804187bfbf55edc56939aab/codex-rs/core/src/agent/control/user_authorization.rs#L30-L30) |
| 21st-dev/1code | Documented worktree-per-chat plus background cloud-sandbox execution — [README#L88](https://github.com/21st-dev/1code/blob/9f1bc76fa4372c18c565b5a4f8daf38ae3595f0e/README.md#L88-L88), [#L44-L48](https://github.com/21st-dev/1code/blob/9f1bc76fa4372c18c565b5a4f8daf38ae3595f0e/README.md#L44-L48) | Plan mode requires user review/approval before the agent acts — [README](https://github.com/21st-dev/1code/blob/9f1bc76fa4372c18c565b5a4f8daf38ae3595f0e/README.md#L77-L82) |

**Decision questions before prototyping a bounded loop:** What is the actual failure mode when the step/turn cap is hit mid-task — silent stop, error, or user handoff? Is the cap a hard safety limit or a cost control, and does your workload need both? tiny-agent's cap is a simple counter; harness-sdk's controls are richer (cancellation, retries, concurrency guards) but need a prototype run against a real multi-tool task before assuming feature parity with your target workload.

## Delegation and sub-agents

- OpenCode ships two built-in primary agents switchable with Tab — `build` (full access) and `plan` (read-only, denies edits, asks before bash) — plus a `@general` subagent — [README#L104-L108](https://github.com/anomalyco/opencode/blob/df23b7f9488a38e6f8064a0739d4f8cde86d7cfb/README.md#L104-L108), [#L102](https://github.com/anomalyco/opencode/blob/df23b7f9488a38e6f8064a0739d4f8cde86d7cfb/README.md#L102-L102), [#L110-L111](https://github.com/anomalyco/opencode/blob/df23b7f9488a38e6f8064a0739d4f8cde86d7cfb/README.md#L110-L111). This is defined in code with a schema for mode, permission ruleset, model, prompt, temperature, topP, and steps — [agent.ts](https://github.com/anomalyco/opencode/blob/df23b7f9488a38e6f8064a0739d4f8cde86d7cfb/packages/opencode/src/agent/agent.ts#L35-L56). Its "plan" agent's permission config denies all edit tools except plan files under `.opencode/plans`, and denies the general task subagent — a concrete least-privilege sub-agent pattern — [agent.ts](https://github.com/anomalyco/opencode/blob/df23b7f9488a38e6f8064a0739d4f8cde86d7cfb/packages/opencode/src/agent/agent.ts#L140-L265).
- Strands' Python SDK implements delegation as a plugin: a `delegate=True` tool must be the only tool called in that turn, ends the loop via `end_turn`, and streams delegate events — [_agent_delegation.py#L1](https://github.com/strands-agents/harness-sdk/blob/08ed4cfd3eb42ae9f668595e675d5f196eee7e44/strands-py/src/strands/agent/_agent_delegation.py#L1-L1), [#L3](https://github.com/strands-agents/harness-sdk/blob/08ed4cfd3eb42ae9f668595e675d5f196eee7e44/strands-py/src/strands/agent/_agent_delegation.py#L3-L3), [#L5-L9](https://github.com/strands-agents/harness-sdk/blob/08ed4cfd3eb42ae9f668595e675d5f196eee7e44/strands-py/src/strands/agent/_agent_delegation.py#L5-L9), [#L73-L74](https://github.com/strands-agents/harness-sdk/blob/08ed4cfd3eb42ae9f668595e675d5f196eee7e44/strands-py/src/strands/agent/_agent_delegation.py#L73-L74), [#L76-L77](https://github.com/strands-agents/harness-sdk/blob/08ed4cfd3eb42ae9f668595e675d5f196eee7e44/strands-py/src/strands/agent/_agent_delegation.py#L76-L77). Delegation is rejected on stateful models to avoid an unclosed server-side function call — [same file](https://github.com/strands-agents/harness-sdk/blob/08ed4cfd3eb42ae9f668595e675d5f196eee7e44/strands-py/src/strands/agent/_agent_delegation.py#L97-L110).
- 1Code documents custom sub-agents as a visual sidebar task list — [README](https://github.com/21st-dev/1code/blob/9f1bc76fa4372c18c565b5a4f8daf38ae3595f0e/README.md#L11-L34); the mechanics behind that UI are unknown here.

**Decision question:** does the workflow need a hard single-tool-per-turn delegation rule (Strands) or a broader capability fence per agent role (OpenCode)? Not drop-in substitutes; reproduce the stateful-model rejection before trusting delegation with a stateful provider.

## Tool and permission boundaries

| Repo | Mechanism | Source |
|---|---|---|
| anomalyco/opencode | Rulesets with allow/ask/deny actions; default asks before reading `.env`, denies the `question` tool, gates external directories, whitelists skill/reference dirs | [agent.ts](https://github.com/anomalyco/opencode/blob/df23b7f9488a38e6f8064a0739d4f8cde86d7cfb/packages/opencode/src/agent/agent.ts#L98-L117) |
| aannoo/hcom | Remote `config_get`/`config_set` refuse `relay_psk`, `relay_token`, `relay_id`, and the broker URL; PSK file kept at mode 0600 on Unix | [README#L183](https://github.com/aannoo/hcom/blob/fabb309b57cb33b39c69b773cd759723a10e94b5/README.md#L183-L183), [#L181](https://github.com/aannoo/hcom/blob/fabb309b57cb33b39c69b773cd759723a10e94b5/README.md#L181-L181) |
| openai/codex | Admin-only `allow_managed_hooks_only = true`, honored only in `requirements.toml` (not `config.toml`), to lock out user/project/session hooks | [config.md](https://github.com/openai/codex/blob/6f39a47bb3b04de4c804187bfbf55edc56939aab/docs/config.md#L11-L15) |
| openai/codex | Separate sandboxing/approvals doc and an execution-policy rules system exist as pages, referenced but not detailed in this snapshot | [docs/sandbox.md](https://github.com/openai/codex/blob/6f39a47bb3b04de4c804187bfbf55edc56939aab/docs/sandbox.md#L3-L3), [docs/execpolicy.md](https://github.com/openai/codex/blob/6f39a47bb3b04de4c804187bfbf55edc56939aab/docs/execpolicy.md#L3-L3) |
| 21st-dev/1code | Plan mode: agent's proposed plan must be reviewed/approved or modified before it acts | [README](https://github.com/21st-dev/1code/blob/9f1bc76fa4372c18c565b5a4f8daf38ae3595f0e/README.md#L77-L82) |

hcom's own documented limitations belong here too: its relay is a single all-or-nothing trust domain with no scoped roles, read-only peers, or per-device permissions ([README#L158](https://github.com/aannoo/hcom/blob/fabb309b57cb33b39c69b773cd759723a10e94b5/README.md#L158-L158)), and a leaked shared PSK cannot be revoked ([#L191](https://github.com/aannoo/hcom/blob/fabb309b57cb33b39c69b773cd759723a10e94b5/README.md#L191-L191)); it also trusts the local user account and does not defend against **another user on the same account** or filesystem-level malware on the same host — [#L174-L177](https://github.com/aannoo/hcom/blob/fabb309b57cb33b39c69b773cd759723a10e94b5/README.md#L174-L177). These are the project's own documented statements, not an independently verified security assessment; nothing here is a security guarantee for any repository.

**Decision questions:** is the boundary you need per-tool (OpenCode's ruleset), per-transport-secret (hcom's field redaction), per-config-file authority (Codex's `requirements.toml` split), or human-in-the-loop (1Code's plan approval)? A prototype should exercise the deny path, not just the allow path, before a permission model is trusted.

| openai/codex | Root thread history filtered and capped at 8 messages for MultiAgent V2 authorization | [user_authorization.rs#L48-L230](https://github.com/openai/codex/blob/6f39a47bb3b04de4c804187bfbf55edc56939aab/codex-rs/core/src/agent/control/user_authorization.rs#L48-L230), [#L30](https://github.com/openai/codex/blob/6f39a47bb3b04de4c804187bfbf55edc56939aab/codex-rs/core/src/agent/control/user_authorization.rs#L30-L30) |
| 21st-dev/1code | Persistent memory documented via CLAUDE.md and AGENTS.md file support | [README](https://github.com/21st-dev/1code/blob/9f1bc76fa4372c18c565b5a4f8daf38ae3595f0e/README.md#L11-L34) |

OpenCode also documents an unresolved design ambiguity worth noting before extending its hook surface: a legacy `experimental.chat.system.transform` hook can arbitrarily mutate the baseline system prompt, while V2 plugins have no equivalent hook — [CONTEXT.md](https://github.com/anomalyco/opencode/blob/df23b7f9488a38e6f8064a0739d4f8cde86d7cfb/CONTEXT.md#L225-L225).

**Decision question:** does your workload need durable file-backed memory (1Code's convention files), a typed context-source model (OpenCode), or is a simple bounded ring buffer (tiny-agent, Codex's root cap) sufficient? Bounded buffers are cheap to prototype and audit; typed context assembly is more expressive but has more surface to get wrong.

Strands defaults to Amazon Bedrock (AWS credentials required), with Anthropic, OpenAI, Gemini, and Ollama configurable — [README](https://github.com/strands-agents/harness-sdk/blob/08ed4cfd3eb42ae9f668595e675d5f196eee7e44/README.md#L59-L59) — a provider-lock-in question worth resolving early. hcom is a single Rust binary with no background services — [README](https://github.com/aannoo/hcom/blob/fabb309b57cb33b39c69b773cd759723a10e94b5/README.md#L9-L9). Deployment cost and footprint have not been measured across these candidates.

## Prototype checklist before selecting a feature

1. Reproduce the loop bound (step/turn/token cap) against a task shaped like your real workload, not a toy prompt.
2. Exercise the deny/ask path of any permission ruleset, not only the allow path.
3. Confirm whether a "development practice" claim (build/test/CI commands, contributing guides) is being read as such and not folded into a runtime-behavior decision.
4. Check whether the state/memory pattern's cap or eviction rule matches your task's actual context growth, not its steady-state size.
5. If evaluation matters to the decision, locate an actual harness or scoring mechanism in the source before trusting a README's mention of "evals."
